# Критерий завершения change

Change завершён, когда подтверждены все обязательные изменённые требования и
затронутые потребители. Отметка tasks и `openspec validate` сами по себе этого не доказывают.

## Доказательства

В существующем `openspec/changes/<name>/verification.md` либо в разделе Verification
файла tasks.md ведём короткую таблицу. Отдельного реестра требований не создаём.

| Требование | Сценарий | Проверка | Результат | Ограничения |
| --- | --- | --- | --- | --- |
| Ссылка на delta/main spec и точное имя Requirement | Имя Scenario; отдельные строки для разных проверок | Команда + test/node ID либо воспроизводимая ручная проверка | passed / failed / blocked / not-run, дата и проверенная версия | Непроверенные границы или «нет в заявленной области» |

Правила таблицы:

- Каждое добавленное, изменённое, удалённое или переименованное требование имеет
  сценарий и доказательство. Для удаления проверяем миграцию/отсутствие прежнего
  поведения; для переименования — сохранение смысла и ссылок.
- Все обязательные сценарии требования отражены, в том числе затронутые ошибки и
  состояния существующих данных. Один тест может подтверждать несколько строк.
- Для границы указываем потребителя: клиент, соседний сервис, worker или AI. Проверка
  только producer не подтверждает изменённый вызывающий сценарий.
- `passed` означает выполненную проверку заявленного свойства. Сборка, collection
  и skipped не выдаются за успешный тест поведения. Для бага указываем исходное
  воспроизведение; его отсутствие остаётся явным ограничением.
- Невыполненная обязательная гарантия с failed/blocked/not-run **блокирует завершение**.
  Принятие исключения или уменьшение scope требует явного согласования и обновления
  spec/design/tasks; запись в колонке «Ограничения» сама по себе не разрешает обход.
- Чисто документационный/tooling change перечисляет свои критерии и подходящие
  проверки; если нет spec delta, это явно отмечается, фиктивные продуктовые требования не создаются.

## Итоговая сверка

Перед объявлением завершения сверить таблицу с delta specs и реализацией, убедиться,
что обязательные проверки прошли на итоговой версии, а tasks соответствуют результатам.
Указать окружение, команды и оставшиеся ограничения. Подтвердить согласованность
потребителей, миграций/выпуска, решений и edge cases в заявленном scope.
Перед архивированием синхронизировать delta с main specs; новые согласованные политики
не объявлять уже внедрёнными во всём приложении.

## Локальные обязательные проверки

Установка для каждого checkout (pre-commit >= 3.2, Python >= 3.12 и OpenSpec в PATH):

```sh
pre-commit install --hook-type pre-commit --hook-type pre-push
```

- `pre-commit`: существующий Ruff и быстрая строгая валидация OpenSpec на каждом commit,
  включая удаления и вызов `pre-commit run --all-files`.
- `pre-push`: проверка отправляемого Git диапазона, OpenSpec и выбранные безопасные
  тестовые наборы. Checkout должен соответствовать отправляемому HEAD и быть чистым.
- При неизвестной runtime-области, ошибке тестов или отсутствии инструмента hook
  возвращает ошибку. Новый затрагивающий область change добавляет безопасный набор
  в `scripts/check_changed.py` после чтения fixtures. Обычный `pytest` по всему repo не запускается.

Ручной запуск текущих изменений, включая untracked, до commit:

```sh
python3 scripts/check_changed.py --worktree --list
python3 scripts/check_changed.py --worktree
```

Просмотр выбора для явно заданной границы:

```sh
python3 scripts/check_changed.py --files services/rpe-service/rpe_service/schemas.py --list
```

Начальная карта включает workflow/gate, plan-contracts и RPE. Наборы являются
ограниченной регрессией: например, plan-contracts проверяет выбранные операции
планов, а не все функции plans/workouts/gateway. При изменении другой функции
добавляем её проверку; полноту подтверждает таблица change и review.
Изменения общих proto/библиотеки/dependencies выбирают оба сервисных набора.
Plan-contracts использует disposable Docker PostgreSQL/Redis, задавая URL до импорта
сервисов, включая supplements; RPE не требует БД.
Ни один набор не подключается к Neon/VPS или локальной БД приложения.

При вводе hooks 2026-11-12 plan-contracts воспроизвёл [ошибку retry logger](../edge-cases/EC-20261112-cleanup-retry-logger.md):
42 passed, 2 failed. До исправления этого дефекта соответствующая проверка push
будет возвращать ошибку. Подробности — в отчёте enforce-change-verification.

Hooks запускают обязательные локальные проверки, но могут быть отключены или
обойдены `--no-verify`/SKIP. Это не серверный CI gate. GitHub Actions не добавлены;
имеющийся publish workflow по-прежнему только собирает и публикует образы.
Автоматический hook не проверяет содержательную полноту таблицы и не доказывает
принятие требований — это критерий итогового review.

Механика стадий и диапазона сверена с [документацией pre-commit](https://pre-commit.com/#pre-push).
