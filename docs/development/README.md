# База процесса разработки

Это начальная организация работы, а не описание согласованного поведения продукта.
Владелец выбирает области спецификаций; требования обсуждаются внутри выбранной области.

## Где что хранится

| Артефакт | Назначение | Когда обновлять |
| --- | --- | --- |
| [AGENTS.md](../../AGENTS.md) | Правила работы и маршрутизация контекста | Изменился устойчивый процесс |
| [OpenSpec config](../../openspec/config.yaml) | Контекст и правила создания артефактов | Изменились правила работы со specs |
| `openspec/specs/<capability>/spec.md` | Согласованное актуальное поведение | Внедрено и проверено изменение требований |
| `openspec/changes/<change>/` | Предложение, delta specs, дизайн, задачи | В ходе конкретного изменения |
| [Edge cases](../edge-cases/README.md) | Воспроизводимые пограничные дефекты | Найден, исправлен или снова проявился случай |
| [Решения](../decisions/README.md) | Причины и границы договорённостей | Решение предложено, принято или заменено |
| Тесты сервисов, `tests/e2e/` | Исполняемая проверка поведения | Меняется поведение или исправляется дефект |
| [Кандидаты specs](spec-candidates.md) | Очередь обсуждения | Выбрана или отклонена область |

Change ссылается на требования, решения и edge cases; edge case — на проверку и
требование; решение — на затронутые specs и изменения. Не копируем одно требование
во все документы: spec хранит **что**, решение — **почему**, edge case —
**при каких условиях ломалось и как проверить снова**.

## Рабочий цикл

1. Определить поведение, прочитать релевантные код, tests и память проекта.
2. Для новой спецификации предложить область и сценарии. Обсудить спорные правила,
   записать договорённости, не превращая предположение в консенсус.
3. Для изменения поведения создать OpenSpec change с критериями приёмки.
   Локальную правку внутри существующих требований можно делать без change.
4. Реализовать согласованный объём. Для дефекта сохранить воспроизведение и
   регрессионный тест на минимальном уровне, способном поймать дефект.
5. Проверить сценарии и контракты. В tasks change или edge case записать команду,
   окружение, результат и ограничения.
6. Сверить документы с реализацией, обновить память, синхронизировать specs и
   архивировать завершённый change. Незавершённую работу не помечать выполненной.

## OpenSpec

На момент настройки установлен CLI **1.16.1**, используется стандартный `spec-driven`.
Отдельную схему для edge cases и решений пока не вводим: эти записи живут дольше
одного change и создаются по необходимости.

Интеграция Codex сгенерирована в `.agents/skills/`; локальная интеграция Devin сохранена.
`openspec/` и `.agents/skills/` предназначены для Git. Проектные правила храним в config
и AGENTS.md, а не в сгенерированных skills. Коммит выполняется отдельно.

Команды из корня репозитория:

```sh
openspec list
openspec list --specs
openspec new change <change-name>
openspec status --change <change-name>
openspec instructions proposal --change <change-name>
openspec validate --all --strict --no-interactive
```

`new change` создаёт каркас; содержание нужно подготовить отдельно. Доступны skills
explore, propose, update, apply, sync и archive. Наличие файла и статус OpenSpec
`done` не доказывают согласование или реализацию. Основные specs содержат первые три capability: применение плана, перенос расписания
и массовую правку. Покрытие всего продукта пока не заявляется.
Проверяемый пример полного цикла: [отчёт](plan-contract-verification.md).

## Проверки и окружение

- Python workspace описан в `pyproject.toml`; тесты сервисов имеют собственные импорты
  и зависимости. Команды подбираются после чтения конкретных tests/fixtures.
- E2E используют `GATEWAY_BASE_URL` (по умолчанию `http://localhost:8000`) и
  `INTERNAL_GATEWAY_SECRET`; нужен локальный тестовый стек. E2E могут менять данные,
  поэтому используют отдельное тестовое окружение.
- `.github/workflows/publish-images.yml` собирает и публикует образы; шагов тестирования
  там сейчас нет. Проверки в документации пока являются правилами, а не CI gate.
- `make sync`/`makemigrations` применяют и создают миграции нескольких сервисов.
  Это не команды проверки документации или безусловной подготовки окружения.

## Дополнения на обсуждение

| Дополнение | Польза | Предложение сейчас |
| --- | --- | --- |
| Инварианты домена | Защищать общие правила разных операций | Раздел внутри выбранных specs, без отдельного реестра |
| Проверки контрактов сервисов | Ловить регрессии на границах plans/workouts/gateway | Обсудить после первых specs |
| Eval-сценарии AI | Проверять выбор инструментов и интерпретацию запросов | После выбора области AI-агента |
| Runbooks восстановления | Повторять проверенные действия при сбоях | По факту появления сценария |
| Проверка документов и регрессий в CI | Сделать проверки обязательными | Отдельное изменение после обсуждения |

Отдельные журналы ежедневных отчётов, рисков и тестовых прогонов пока не создаём:
достаточно change/tasks, решений и edge cases.

Механика сверена с [AGENTS.md в Codex](https://developers.openai.com/codex/guides/agents-md)
и [конфигурацией OpenSpec](https://openspec.dev/docs/configuration/config-yaml).
