# Применение плана: контракт API и совместимость

Обычный `POST /api/v1/plans/applied-plans/apply/{plan_id}` применяется при отсутствии
активного плана. При активном плане ответ — HTTP 409. Для явной замены клиент
передаёт query-параметр `replace_active=true`. Аналогичный параметр поддерживает
`apply-async/{plan_id}`. Обязательные `user_max_ids` и compute body сохраняются.

Успешная постановка async-задачи означает принятие в очередь. Клиент опрашивает
`/api/v1/plans/applied-plans/tasks/{task_id}`: только `SUCCESS` означает успешное
завершение применения; доменная ошибка завершается `FAILURE`, без ложного `SUCCESS`
с вложенным `ok=false`.

Пока пакеты создаются, отдельные тренировки могут временно появляться в списке.
При сбое не начатые тренировки удаляются. Начатые/завершённые сохраняются отдельно
с прогрессом, без связи с неуспешным планом. Для повторной очистки необходим worker
очереди `plans.tasks`; для async-правки и переноса — `workouts.tasks`.
Оба worker добавлены в production compose; для очистки у plans-service и worker
должен быть тот же `INTERNAL_GATEWAY_SECRET`, что и у workouts-service.

## Проверка потребителей 2026-11-12

- Gateway проксирует query-параметры и HTTP 409; HTTP/Celery тесты проходят через
  его реальные маршруты применения и статуса задачи.
- В agent-service прямых вызовов endpoint применения не найдено. Его массовая
  правка и перенос продолжают использовать существующий формат команд.
- В соседнем Flutter checkout (`3546430` + рабочее дерево) обновлены
  `PlanApi.applyPlanAsync`, `PlanApi.applyPlan` и экран `CalendarPlanDetail`.
  После HTTP 409 экран предлагает подтверждение замены. При подтверждении
  повторяется запрос с `replace_active=true`, при отмене новый запрос не отправляется.
  Другие ошибки не превращаются в предложение замены и не повторяются автоматически.
- API и диалог покрыты тестами `calendar_plan_apply_confirmation_test.dart`;
  совместно с `calendar_plan_actions_test.dart` прошли 14 Flutter-тестов.

Backend и обновлённый Flutter необходимо выпускать согласованно. Уже выпущенные
старые клиенты без этого изменения по-прежнему получат 409 при попытке замены.

## Ограничения восстановления

Очистка имеет восемь фоновых повторов с интервалом 60 секунд. При исчерпании повторов
задача получает FAILURE; при недоступности самого брокера ошибка постановки пишется
в лог `failed_application_cleanup_enqueue_failed`. Это не бесконечная гарантия
восстановления после любой аварии: для таких отказов нужна операционная обработка
ошибки и повтор задачи после восстановления зависимостей. Полноценного outbox
для компенсаций в этом change нет.
