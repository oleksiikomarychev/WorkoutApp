# Предложение: спецификации через модель и контракты

Статус: формат предложен для обсуждения. Приняты только
[три правила применения плана](../decisions/DEC-20261110-plan-application-rules.md).
Документ не вводит новую OpenSpec schema и не подтверждает поведение кода.

## Минимальная единица спецификации

Одна capability описывает:

1. **Модель:** сущности, значимые состояния и связи; без копирования ORM и всех полей.
2. **Инварианты:** свойства, сохраняющиеся во всех допустимых состояниях, с точной областью действия.
3. **Контракты операций:** предусловия, эффект, постусловия, неизменяемые данные,
   исход ошибки. Повторы и конкуренцию описываем, когда они существенны.
4. **Сценарии-свидетели:** несколько примеров к каждому требованию плюс регрессии
   обнаруженных edge cases. Полное перечисление комбинаций не требуется.

Состояния и переходы удобно записывать таблицей; условия — короткими формулами
с определениями. Каждый инвариант или контракт получает стабильный идентификатор.
Сценарий и тест ссылаются на него. Общую гарантию описываем один раз и переиспользуем
ссылкой, лишь когда её семантика действительно одинакова в разных операциях.

## Пример: ApplyPlan

Обозначения: S — состояние в границах операции; k — идентификатор одной операции;
A(S) — активный план пользователя; H(S) — история завершённых тренировок;
C(k) — все согласованные обязательные эффекты применения завершены.
Это логическая модель, не новые поля БД или выбранный протокол.

| ID | Принятая гарантия | Формальная запись |
| --- | --- | --- |
| APPLY-RETRY | Повтор завершённой операции не создаёт новый результат | Повтор k возвращает сохранённый результат k и не добавляет применённых планов |
| APPLY-REPLACE | Замена активного плана явная | A(S) существует и A(S′) ≠ A(S) ⇒ запрошена явная замена |
| APPLY-HISTORY | Замена сохраняет историю | При замене H(S′) = H(S) для данных, затрагиваемых этой операцией |
| APPLY-SUCCESS | Частичный результат не является успехом | success(k) ⇒ C(k) |

Равенство истории относится к эффекту замены, а не запрещает независимое завершение
тренировки другим запросом. Повтор не откатывает последующие независимые изменения.
success ⇒ C не означает, что при сбое никакие промежуточные данные не могли появиться.

Открытые параметры контракта: как распознаётся k (включая двойное нажатие), что делать
с повтором ещё выполняющейся операции, какие эффекты входят в C, что возвращать при
конкурирующих заменах и как восстанавливать незавершённую операцию. Это реальные
продуктовые/технические развилки; формализация делает их видимыми, но не решает сама.

## Как получать проверки и edge cases

Для каждой операции рассматриваем только применимые измерения: допустимое/недопустимое
состояние, пустая/граничная выборка, повтор, конкурирующее изменение, сбой до/после
существенного эффекта. Выбираем представителей классов и рискованные сочетания,
а не полное декартово произведение.

Например, APPLY-RETRY проверяется последовательностью «применить → повторить →
сравнить результат и число созданных планов». Разные допустимые входные данные
можно генерировать property-based тестом; допустимые последовательности операций —
тестом модели переходов, если сложность этого оправдывает.

Найденный баг становится записью edge case с нарушенным ID и минимальным примером.
Если случай уже следует из контракта, добавляем регрессию без нового требования.
Если контракт допускает обе трактовки, уточняем его и фиксируем решение.

## Размещение в OpenSpec

После согласования формата модель и общие определения помещаем в capability spec,
гарантии — в стандартные Requirement с Scenario. Решения о реализации остаются
в design и docs/decisions. Этот документ — методический пример, не второй источник
действующих требований. При переносе примера в spec заменяем его ссылкой.
AGENTS.md хранит порядок работы, а не каталог бизнес-правил.
