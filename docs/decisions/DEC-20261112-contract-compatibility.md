## Контекст

При введении replace_active серверная замена плана стала несовместимой с прежним
Flutter-вызовом, хотя первое применение продолжало работать. Случай показывает
необходимость проверять потребителя и существующее состояние. Наличие генератора
protobuf, миграций и сборки образов само по себе не подтверждает совместимость.

## Решение

1. **Изменение контракта учитывает потребителей.** При изменении API, событий,
   WebSocket, единиц или смысла полей определяются затронутые сервисы, клиенты и
   AI-инструменты. Проверяются вызывающие сценарии, включая ошибки и существующие данные.
2. **Переход между версиями спланирован.** Для несовместимого изменения определяются
   поддерживаемые сочетания версий, порядок выпуска, миграция данных и способ
   восстановления при неудаче. Неожиданная поломка старого клиента не считается
   завершённым переходом.
3. **Исходный контракт, реализация и производные файлы согласованы.** Изменения
   `.proto` проходят через генерацию; схемы данных согласуются с миграциями;
   клиентские модели — с фактическими ответами. Сборка и валидация документов
   дополняются проверкой затронутого сценария.

Границы совместимости задаёт конкретный change. Постоянная поддержка всех старых
версий и отдельная версия API для каждой правки не требуются. Способ восстановления
при неудаче выбирается с учётом реальных изменений данных; автоматическая обратимость
любой миграции не обещается.

## Альтернативы и причины

Проверка только producer не выявляет расхождение реального вызова и нового контракта.
Проверки потребителей и плана перехода ограничиваются областью change, чтобы не
требовать полного аудита приложения или бессрочной совместимости при каждой правке.

## Последствия

COMPAT принят как целевой контракт. Каждый затрагивающий границу change определяет
потребителей и применимые проверки, а несовместимый — также план перехода.
Полное соответствие существующей реализации не установлено. Runtime, миграции,
клиент и основные specs этим шагом не меняются.

## Проверка и пересмотр

Проверяется цепочка «потребитель → изменённый контракт → наблюдаемый результат».
Для постепенного выпуска проверяются необходимые сочетания версий, а для изменения
данных — применимая миграция существующего состояния и выбранный способ восстановления.
Генерация/сборка не заменяют вызывающего сценария.

Здесь проверяются только документы и конфигурация OpenSpec. Повторный запуск
сервисных/клиентских тестов, генерация stubs, миграции и deployment не выполнялись;
результаты реализующих проверок фиксируются в соответствующих changes.
