# Общий контракт готовности и отказов зависимостей

- Статус: accepted
- Дата: 2026-11-12
- Область / сервисы: готовность возможностей приложения, конфигурация и зависимости
- Связи: [READY](../architecture/shared-contracts-draft.md#ready--готовность-capability-и-конфигурация), [анализ влияния](../architecture/change-impact.md), [очередь](../architecture/change-roadmap.md), [PostgreSQL без SQLite fallback](DEC-20261112-postgresql-without-sqlite-fallback.md)
- Кем и когда согласовано: владелец проекта в чате 2026-11-12
- Основание: на предложение трёх правил — готовность функции, явная конфигурация/ограничения и ограничение сбоя с проверкой восстановления — владелец ответил «отлично».
- Заменяет / заменено: —

## Контекст

Просмотренные health endpoints plans/workouts/RPE возвращают статическое `ok`.
RPE допускает продолжение запуска после ошибки предварительной загрузки расчётной
таблицы. Эти ответы подтверждают работу HTTP-процесса, но сами по себе не доказывают
готовность операций. Поведение при отказе и восстановлении здесь не воспроизводилось.

## Решение

1. **Готовность означает способность выполнить заявленную функцию.** Работающий
   HTTP-сервер сам по себе не подтверждает доступность БД, нужной схемы, расчётных
   ресурсов или обработчика очереди. Проверки учитывают зависимости конкретной
   возможности; работоспособность процесса и готовность функции различаются.
2. **Конфигурация и ограничения явные.** Различаются отключённая, временно недоступная,
   работающая с ограничениями и полностью готовая возможность. Работа с ограничениями
   допустима только по определённому правилу. Принятый запрет SQLite и подмены
   PostgreSQL сохраняется, включая локальный запуск приложения.
3. **Сбой ограничен затронутыми возможностями, восстановление проверяемо.** Отказ
   зависимости делает недоступными функции, которым она нужна; независимые функции
   продолжают работать. После возвращения зависимости проверяется восстановление
   реального сценария.

Обязательные возможности каждого окружения, условия остановки запуска, конкретные
ответы пользователю и способ восстановления определяются отдельно в соответствующем
change. Единый набор health endpoints, автоматическое восстановление без перезапуска
и обязательный запуск всего стека для любой локальной задачи не предписываются.
Текущая доступность только локального PostgreSQL не является отказом всех окружений
и не разрешает заменять хранилище.

## Альтернативы и причины

Единый статус работающего процесса недостаточен для вывода о готовности функций.
Учет зависимостей каждой возможности позволяет сохранять независимые сценарии
доступными и явно обозначать ограничения затронутых операций.

## Последствия

READY принят как целевой контракт. В реализующем change перечисляются возможности,
их зависимости и критерии готовности. Соответствие всего приложения не подтверждено;
runtime, окружения и основные specs этим шагом не меняются.

## Проверка и пересмотр

Проверяется последовательность «зависимость доступна → отказала → восстановилась»
с сопоставлением готовности функции и результата операции. Для применимой границы
проверяются также отключённая возможность, отсутствие конфигурации/нужной схемы,
неработающий обработчик очереди и сохранение независимого сценария.

Здесь проверяются только документы и конфигурация OpenSpec. Сервисы, БД, очереди
и тесты восстановления не запускались. Способ и результат восстановления будут
зафиксированы в реализующих changes.
