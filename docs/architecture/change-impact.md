# Область влияния конкретного change

Это введённое правило рабочего процесса. В [каталоге](shared-contracts-draft.md)
ACCESS, EXEC, DATA, EVENT, READY и COMPAT приняты как целевые контракты.
Статус требования и подтверждение реализации различаются.

## Минимальная запись в proposal

| Поле | Что написать |
| --- | --- |
| Намерение | Какая наблюдаемая проблема или возможность меняется |
| Возможности | ID из карты; для новой области добавить её в карту |
| Границы | Producer → consumer, DB/event/worker/cache/UI и соседний репозиторий, если затронуты |
| Семейства контрактов | ACCESS / EXEC / DATA / EVENT / READY / COMPAT: применимо, не применимо с короткой причиной или неизвестно |
| Источник требования | Действующая spec/решение либо новое предложение; draft не выдаётся за принятое |
| Проверки | Какие свойства, конкретные consumer paths и регрессии подтвердят результат |
| Выпуск | Требуется ли совместимый клиент, миграция, worker/profile и какое ограничение остаётся |

Таблица — формат мышления, не обязательный длинный шаблон: для малой локальной
правки достаточно короткого абзаца с применимыми полями. Отсутствие изменения
поведения по-прежнему не требует создавать OpenSpec change.

## Порядок применения

1. Найти изменяемую capability и её прямые границы в карте. Прочитать актуальные
   specs, связанные решения и edge cases.
2. Пройти шесть семейств как вопросы к change. Они не становятся новыми продуктовыми
   требованиями без согласования. Принятые правила шести семейств и другие связанные решения
   применить к затронутой области. «Неизвестно» порождает конкретную задачу исследования.
3. Проверить прямых потребителей. Расширять область дальше только если меняется
   наблюдаемый контракт следующей границы. Не запускать весь аудит приложения заново.
4. Решения об ожидаемом поведении вне принятого контракта принести владельцу.
   Обычные технические решения внутри согласованного объёма принимать самостоятельно.
5. Реализовать и выполнить проверки на подходящем уровне. Новые рискованные свойства
   по возможности проверять генерацией вводов, последовательностей и внедрением сбоев.
6. Проверить, что заявленный scope действительно выполнен у всех перечисленных
   потребителей. Обновить карту/решения/регрессии и синхронизировать main specs.

## Применение принятого ACCESS

Для затронутого доступа сослаться на [решение](../decisions/DEC-20261112-access-contract.md):
указать инициатора, владельца/область данных, действие и основание разрешения.
Проверить, что подмена пользователя, объекта или пути вызова не расширяет права;
отказ подтверждения прав не открывает персональные данные. Включить затронутые
worker/cache/AI paths и разрешённый сценарий. Не выводить конкретные права тренера
или политику отзыва из общего контракта; использовать принятое правило capability.

## Применение принятого EXEC

Для затронутой операции сослаться на [решение](../decisions/DEC-20261112-operation-execution-contract.md)
и указать, как проверяются ошибка зависимости, соответствие результата эффектам
и выбранная политика частичного сбоя. Проверить путь до клиента/AI, если они
сообщают итог операции. Уже согласованную политику операции использовать повторно.
Это не требует исправлять все остальные операции приложения в том же change.

## Применение принятого DATA

Для затронутых данных сослаться на [решение](../decisions/DEC-20261112-data-semantics-contract.md):
указать смысл/единицы полей, допустимость значений, точность, отсутствие/default,
источник и роль данных. Проверить смысл при преобразовании и сохранении, согласованность
затронутых путей ввода с учётом операции и влияние правки исходника на зависимые
данные. Числовые границы и пересчёт истории использовать из capability или согласовать
в change; общий DATA их не назначает.

## Применение принятого EVENT

Для затронутого потока сослаться на [решение](../decisions/DEC-20261112-event-delivery-contract.md):
указать идентичность/повторы, значимый порядок, этапы подтверждения и политику
восстановления или неуспешного исхода. Проверить цепочку «событие → эффект →
подтверждение» с повтором и перезапуском между этапами. Для затронутых проекций
проверить insert/update/delete, совместимость и распознавание отставания в выбранном
reader. Сроки, число повторов и задержку взять из контракта потока или согласовать
в change; общий EVENT их не назначает.

## Применение принятого READY

Для затронутой возможности сослаться на [решение](../decisions/DEC-20261112-capability-readiness-contract.md):
указать зависимости, критерии готовности и режимы работы. Проверить отказ и возврат
зависимости реальной операцией, сохранение независимых функций и применимые ошибки
конфигурации. Обязательность возможностей по окружениям и реакцию запуска/API взять
из их контракта либо определить в change; общий READY не назначает их автоматически.

## Применение принятого COMPAT

Для затронутого контракта сослаться на [решение](../decisions/DEC-20261112-contract-compatibility.md):
перечислить потребителей и проверить их сценарии, включая ошибки и существующее
состояние. Для несовместимого изменения указать сочетания версий, порядок выпуска,
миграцию и восстановление. Сверить исходный контракт, сгенерированные файлы, модели
и реализацию. Объём перехода определяется change, бессрочная совместимость не требуется.

## Пример: изменение единицы веса

DATA затрагивает хранение, вычисления и внешнее представление. COMPAT — клиент,
HTTP/gRPC и события; EVENT — если поле попадает в CDC. ACCESS может быть не затронут,
если область доступа не меняется. READY затронут, если нужна миграция или новые
ресурсы. EXEC затронут, если меняется поведение частичного импорта/вычисления.

Итог — один change с ограниченной картой влияния и повторно используемыми свойствами,
а не отдельная spec для каждого числового примера.

## Что этот механизм не автоматизирует

OpenSpec config добавляет инструкции агенту, а validator проверяет структуру.
Автоматического вывода всех зависимостей, проверки принятия контракта и обязательного
CI gate здесь пока нет. Они предлагаются отдельным change в очереди.
