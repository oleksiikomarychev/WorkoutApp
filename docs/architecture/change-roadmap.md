# Предлагаемые rollout changes

Статус: **кандидаты**, не согласованные runtime-изменения и не запущенные работы.
Карта и семейства охватывают приложение; каждый change ниже ограничен конкретным
улучшением. Приоритет — рекомендация по наблюдениям, не утверждение о тяжести
воспроизведённого инцидента.

| Очерёдность / change | Общий контракт и первая область внедрения | Проверяемый результат | Что нужно решить до реализации |
| --- | --- | --- | --- |
| P0 `define-supplements-data-boundary` | ACCESS, DATA, COMPAT: supplements sessions → workouts → gateway/Flutter | Путь gateway → supplements проверен; Actor A не читает/не меняет личные записи B; тип user_id согласован | Продукты общие, рационы персональные — принято. Остаются права редактирования каталога/доступа к рациону и назначение supplement/medication |
| P0 `make-capability-readiness-explicit` | READY: supplements DB, agent queues, profile аналитики | Рабочая БД — PostgreSQL без SQLite fallback; отказ не подтверждает несохранённую запись; выключенная возможность имеет определённый ответ | Запрет SQLite принят; остаются реакция API/запуска на отказ и обязательные/отключаемые capabilities |
| P1 `make-rule-execution-outcomes-explicit` | EXEC, COMPAT: MacroApplier → вызывающий API/task → AI/client result | Недоступный источник не превращается в no-op success; результат частичной правки различим | Для макросов допустим partial result или нужен rollback? |
| P1 `isolate-contract-checks-in-ci` | Процесс проверки: безопасные fixtures, область влияния и CI gate | Выбранные contract tests и specs validation обязательны; suite не импортирует production session factory для очистки данных | Порог и длительность обязательного gate — техническое предложение после измерения, не продуктовая семантика |
| P1 `align-strength-value-semantics` | DATA, COMPAT: RPE ↔ user-max ↔ exercise/sets DTO и клиент | Create/update и HTTP/gRPC одинаково интерпретируют границы, неизвестное, единицы и округление; property tests | Принять единицы/диапазоны/политику некорректного значения; владельца definition vs instance |
| P2 `verify-cdc-recovery-and-deletion` | EVENT, READY: одна representative source table → Kafka → raw → выбранная витрина/reader | Insert/update/delete, duplicate replay и restart проверены целой цепочкой | Реальный reader и требуемая свежесть; production-топология CDC |
| P2 `validate-agent-tool-effects` | ACCESS, EXEC, DATA: selected tool families и их targets | Model-generated arguments проверены до эффекта; результат инструмента корректно отображён; ошибки не объявляются выполнением | Какие инструменты изменяют данные и где уже есть достаточно явное намерение пользователя? Не вводим глобальное подтверждение каждого tool call |
| P2 `align-nutrition-record-semantics` | DATA, COMPAT: plan nutrition JSON ↔ food/supplement session ↔ UI | Общий продукт используется в независимых рационах; согласованы единицы, ссылки и источник истины; проверены преобразования | Связь существующих моделей; влияние правки общего описания на существующие рационы |
| P2 `verify-event-delivery-recovery` | EVENT: social/messaging outbox → Redis stream → webhook dispatcher | Restart/повтор/невосстановимый отказ не дают незаявленной потери или ложного подтверждения | Доставка at-least-once, правила retry/ack и реакции получателя на дубликаты |

Очередь можно менять. Если аналитика или messaging критичны для текущих пользователей,
их приоритет поднимается. Не следует запускать все changes одним большим внедрением.

## Почему эти границы

- Первые ACCESS/READY changes реагируют на конкретные OBS-01/02/06/07 из карты.
- EXEC улучшает повторно используемый протокол результата, а не единственный edge case.
- DATA создаёт общие числовые свойства и единый источник семантики вместо списка
  отдельных значений для каждого расчёта.
- EVENT проверяется на representative pipeline, затем применимость расширяется
  следующими changes; один пройденный поток не доказывает все остальные.
- CI gate делает принятые проверки частью разработки, но не назначает недоказанный
  процент покрытия всей системы.

## Первая порция решений владельцу

Согласованные правила и оставшиеся вопросы:

1. **Продукты и рационы — принято:** продукты общие, рационы принадлежат конкретным
   людям. Изменение состава/количества в одном рационе не меняет другой рацион
   или общее описание продукта. [Основание и границы](../decisions/DEC-20261112-shared-foods-personal-diets.md).
   Связь food/session_data/nutrition_plan с этой моделью ещё предстоит проверить;
   правила добавок и лекарств не определяются автоматически.
2. **Отказ постоянной БД — принято:** рабочее хранилище PostgreSQL, без SQLite
   и in-memory fallback, в том числе локально. [Основание и границы](../decisions/DEC-20261112-postgresql-without-sqlite-fallback.md).
   Удаление существующего fallback ещё не выполнено; реакция API/запуска на отказ
   остаётся предметом change. Доступен локальный PostgreSQL; Neon/VPS недоступны.
   Для текущих документов подключение к БД не нужно.
3. **Набор возможностей production:** нужно назвать обязательные и отключаемые
   контуры. Из наличия каталогов, API и compose profile это решение не выводится.
4. **Выполнение операций — принято:** ошибки не маскируются успехом, результат
   соответствует сохранённым изменениям, для нескольких эффектов определяется
   политика сбоя. [Основание и применение](../decisions/DEC-20261112-operation-execution-contract.md).
   Новый change указывает применимость и проверки. Политика сбоя макросов пока
   не выбрана; одинаковый rollback для всех capabilities не назначен.

5. **Принадлежность и полномочия — принято:** инициатор берётся из доверенного
   контекста и различается с владельцем; путь через API/worker/AI не расширяет права;
   разрешения зависят от действия и типа данных. [Основание и применение](../decisions/DEC-20261112-access-contract.md).
   Конкретные права тренера и отложенные задачи после отзыва доступа остаются открытыми.

6. **Смысл и согласованность данных — принято:** у данных определён смысл,
   разные пути ввода применяют согласованную доменную политику, источник и роль
   данных известны. [Основание и применение](../decisions/DEC-20261112-data-semantics-contract.md).
   Диапазоны, точность/округление и обновление исторических снимков определяются
   соответствующими capabilities/changes, а не одним общим default.

7. **События и восстановление — принято:** повторы/порядок не искажают результат,
   подтверждение соответствует завершённому этапу, производные данные согласованы
   с источником. [Основание и применение](../decisions/DEC-20261112-event-delivery-contract.md).
   Число повторов, сроки, допустимое отставание и способ восстановления остаются
   решениями конкретного потока; работоспособность CDC/webhook этим не подтверждается.

8. **Готовность и отказы зависимостей — принято:** готовность подтверждает функцию,
   конфигурация и ограничения явные, сбой ограничен зависимыми возможностями,
   восстановление проверяется реальным сценарием. [Основание и применение](../decisions/DEC-20261112-capability-readiness-contract.md).
   Обязательные возможности каждого окружения, реакция запуска/API и способ
   восстановления определяются отдельно; работоспособность сервисов ещё не проверена.

9. **Совместимость и выпуск — принято:** изменение контракта учитывает потребителей,
   переход версий спланирован, исходный контракт/реализация/производные файлы согласованы.
   [Основание и применение](../decisions/DEC-20261112-contract-compatibility.md).
   Нужные сочетания версий, миграция и способ восстановления определяются в change;
   бессрочная поддержка всех версий не назначена.

Все шесть общих контрактов согласованы как целевые. Приоритеты очереди и конкретные
внедрения этим не утверждены; соответствие сервисов ещё предстоит проверить.

В текущем шаге реализации, миграции, исправления сервисов и main specs
для этих правил не создаются. Кандидат из очереди превращается в OpenSpec change
после выбора его намерения и границ; обычные технические детали затем решает агент.
