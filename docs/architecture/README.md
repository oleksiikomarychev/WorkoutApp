## Как это соответствует OpenSpec

`openspec/specs/` содержит действующие контракты. Предлагаемое изменение поведения
проходит отдельный `openspec/changes/<name>/`: proposal, delta specs, design по
необходимости и tasks. После реализации и проверки delta синхронизируется с main spec.

Общие требования тоже могут быть capability: например, результат фоновой операции
или изоляция персональных записей. Их область применимости должна быть явной.
Семейство требований не становится выполненным всеми сервисами только потому,
что появилась общая spec.

На первом внедрении requirement ограничивается конкретными операциями/границами.
Следующий change расширяет применимость через MODIFIED requirement и добавляет
проверки новых потребителей. Нельзя записать универсальное SHALL в main spec,
а потом несколько месяцев внедрять его, выдавая частичное покрытие за общее.

Карта описывает **факты и неизвестное**, specs — **принятое поведение**, tests —
**доказательства**, решения — **почему выбран конкретный вариант**.

## Границы текущего шага

Общий процесс анализа влияния введён в AGENTS.md и OpenSpec config. Runtime-код,
контракты API, инфраструктура и клиент этим шагом не меняются. Все шесть семейств
приняты как целевые контракты. Детали возможностей и порядок внедрения остаются
открытыми; очередь changes предложена агентом. Также приняты решения о PostgreSQL
и разделении продуктов/рационов. Принятие требований не означает исправления кода
или проверки его соответствия.

Отсутствие замечания в карте не означает корректность модуля. Существующая spec
и найденный файл теста не означают успешный запуск теста или готовность production.
