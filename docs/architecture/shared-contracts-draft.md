# Общие контракты приложения

Статус: **принятые целевые контракты**: ACCESS, EXEC, DATA, EVENT, READY и COMPAT.
Соответствие всего приложения не подтверждено. Шесть семейств дают язык для changes; область внедрения и реальные
проверки фиксируются отдельно. Ни одно из них не скопировано в main specs.
Имя файла с `draft` сохранено для существующих ссылок; статус задают решения ниже.
Отдельно уже приняты решения о [PostgreSQL без SQLite fallback](../decisions/DEC-20261112-postgresql-without-sqlite-fallback.md)
и [общих продуктах / персональных рационах](../decisions/DEC-20261112-shared-foods-personal-diets.md).
Они отмечены в READY и ACCESS; соответствие кода этим решениям ещё не проверено.

Общий контракт описывает наблюдаемое свойство. Выбор SQL lock, outbox, очереди,
библиотеки или схемы JSON относится к design конкретного change.

## ACCESS — принадлежность и полномочия

**Принято владельцем:** [общий контракт принадлежности данных и полномочий](../decisions/DEC-20261112-access-contract.md).
Это целевые требования; полное соответствие существующих сервисов не проверено.

- ACCESS-1: инициатор определяется доверенным контекстом и различается с владельцем
  данных. user_id, идентификатор объекта и экранный контекст сами по себе не дают прав.
- ACCESS-2: API, worker, кеш, внутренний вызов и AI не расширяют разрешения для
  соответствующего действия. Если право подтвердить не удалось, операция с
  персональными данными не выполняется.
- ACCESS-3: права задаются по действию и типу данных. Чтение, изменение и удаление
  могут иметь разные разрешения; общность каталога не даёт всем права редактирования.

Применимость: аккаунты, CRM, личные планы/сессии, supplements session, сообщения,
AI tools. Исключения: публичный каталог и общие справочники могут иметь другую
политику; это не повод добавлять owner-фильтр к каждой таблице автоматически.

Проверяемое свойство: подмена пользователя, объекта или пути выполнения не даёт
дополнительных прав, раскрытия или изменения чужих персональных данных. Проверяем
также отказ подтверждения прав и разрешённый сценарий. Разрешённую таблицу ролей
задаёт capability; применимость к cache/worker/AI фиксирует change.

Принято владельцем: продукты общие, рационы разных людей отдельные. Изменение
состава/количества в рационе A не меняет рацион B или описание общего продукта.
См. [решение и границы](../decisions/DEC-20261112-shared-foods-personal-diets.md).
Права редактирования каталога и доступа тренера этим правилом не определены;
общность добавок/лекарств из него автоматически не следует.

Открыты конкретные права тренера и поведение отложенной задачи после отзыва доступа.
Принятие общего ACCESS эти вопросы не закрывает.

## EXEC — результат и последствия выполнения

**Принято владельцем:** [общий контракт выполнения операций](../decisions/DEC-20261112-operation-execution-contract.md).
Это целевые требования; полное соответствие существующих сервисов не проверено.

- EXEC-1: результат соответствует сохранённым изменениям; принятие в обработку
  различимо с завершением. API, worker, клиент и AI передают фактический результат.
- EXEC-2: ошибка источника данных или исполнителя не маскируется под корректную
  пустую выборку / отсутствие изменений / полный успех.
- EXEC-3: для нескольких эффектов определена политика сбоя: откат, компенсация
  или явно обозначенный частичный результат. Change проверяет выбранную гарантию
  после уже выполненного первого эффекта.

Применимость: обычные mutations, Celery, макросы, AI-команды, batch и внешние вызовы.
Не требуем глобально одной транзакции, одинакового enum статусов или идемпотентности
каждого HTTP POST. Каждая capability выбирает нужную семантику на общей модели.
Обязательный preview и общие гарантии повтора/конкуренции не приняты этим решением.

Проверяемое свойство: если обязательный эффект не выполнен, наблюдаемый итог не
равен полному успеху. Матрица генерирует отказы до/после существенного эффекта,
потерю ответа, повтор и перезапуск там, где они входят в контракт операции.

Открытый вопрос: для исполнения макроса допустим частичный результат с отчётом
или требуется отмена всей операции? Принятое ранее правило массовой правки не
распространяется на макросы автоматически.

## DATA — значения, идентичность и источник истины

**Принято владельцем:** [общий контракт смысла и согласованности данных](../decisions/DEC-20261112-data-semantics-contract.md).
Это целевые требования; полное соответствие существующих сервисов не проверено.

- DATA-1: у величины определены единица, допустимые значения, точность и округление.
  Отсутствие, неизвестное и ноль различаются; преобразования/default следуют явному правилу.
- DATA-2: create/update/import/tool input и API применяют одну доменную политику.
  Различия объясняются смыслом операции, включая пропуск поля при частичном обновлении.
- DATA-3: известны источник и роль данных: исходная сущность, экземпляр, исторический
  снимок или результат вычисления. Копия/кеш не становятся независимым источником
  истины; при правке исходника определены пересчитываемые и сохраняемые данные.

Применимость: RPE/1RM, definition vs instance упражнения, workout sets, nutrition
units, macro rules и данные AI-инструментов. Универсальные числовые границы не
задаём: допустимость RPE, тренировочного веса и дозировки различается.

Проверяемые свойства: при передаче, преобразовании и сохранении данные сохраняют
согласованный смысл. Проверки разных путей ввода учитывают смысл операции и
одинаковое предоставленное значение; пропуск поля в PATCH не равен его обнулению.
Конкретные свойства округления выбираются в соответствующем change. Например:
Для положительного шага и применимого диапазона floor ≤ исходное ≤ ceil, результат
кратен шагу с указанной погрешностью. Другие свойства выводятся из конкретной формулы;
монотонность и обратимость нельзя предполагать для всех расчётов.

Открыты конкретные диапазоны RPE, единицы/округление веса и обновление исторических
снимков. Их определяет соответствующий change; приоритет RPE/1RM остаётся предложением.

## EVENT — доставка, проекции и восстановление

**Принято владельцем:** [общий контракт доставки событий и восстановления](../decisions/DEC-20261112-event-delivery-contract.md).
Это целевые требования; полное соответствие существующих потоков не проверено.

- EVENT-1: поток определяет идентичность события, повторную обработку и значимый
  порядок. Повтор доставки не создаёт лишнего бизнес-эффекта; запоздавшее событие
  обрабатывается по явному правилу.
- EVENT-2: подтверждение соответствует завершённому этапу: публикация, получение
  и выполнение различаются. После сбоя/перезапуска работа восстанавливается либо
  имеет явно зафиксированный неуспешный исход; исчерпание повторов не означает успех.
- EVENT-3: производные данные согласованы с источником по созданию, изменению,
  удалению и формату. Допустимое отставание определено; устаревшие или ещё не
  готовые данные распознаются.

Применимость: CDC, outbox, Redis streams, webhooks, derived analytics.
Exactly-once не вводится глобальным обещанием. Для webhook не обязательно достижима
та же гарантия, что для ClickHouse-проекции; предел задаётся конкретным потоком.

Проверяемые свойства: цепочка «событие → эффект → подтверждение» сохраняет
согласованный смысл при повторе и перезапуске между этапами. Проверки выбранного
reader охватывают insert/update/delete, запоздавшие события, совместимость формата
и распознавание отставания; условия восстановления задаёт поток.

Открыты число повторов, сроки хранения, допустимое отставание аналитики, способ
восстановления и отображение устаревшей витрины. Их определяет соответствующий change.

## READY — готовность capability и конфигурация

**Принято владельцем:** [общий контракт готовности и отказов зависимостей](../decisions/DEC-20261112-capability-readiness-contract.md).
Это целевые требования; полное соответствие существующих сервисов не проверено.

- READY-1: готовность подтверждает способность выполнить заявленную функцию
  с её зависимостями: БД/схемой, расчётными ресурсами, очередью/обработчиком и другими.
  Работающий HTTP-процесс сам по себе не доказывает готовности функции.
- READY-2: отключённая, временно недоступная, работающая с ограничениями и готовая
  возможность различимы. Ограниченный режим определяется явно; запрет SQLite
  и подмены PostgreSQL сохраняется.
- READY-3: отказ зависимости затрагивает нуждающиеся в ней функции; независимые
  продолжают работать. После возврата зависимости проверяется реальный сценарий.

Применимость: возможности запускаемых сервисов. Обязательность CDC/AI и других
возможностей задаётся для конкретного окружения, а не выводится из наличия сервиса.
Общий контракт не требует всего стека для любой локальной задачи.

Проверяемое свойство: «зависимость доступна → отказала → восстановилась» сопоставляется
с готовностью функции и результатом операции; независимый сценарий остаётся доступным.
Для применимой границы проверяются disabled, отсутствие env/схемы/resource и worker
не в той очереди. Способ восстановления определяется конкретным change.

Принято владельцем: рабочие данные приложения — PostgreSQL, без SQLite и in-memory
fallback, включая локальный запуск. См. [решение](../decisions/DEC-20261112-postgresql-without-sqlite-fallback.md).
Это правило не подтверждает соответствие текущего кода. Политика тестовых fixtures
этим обсуждением не определена; автоматическое исключение для «отладки» не вводится.

Открытый вопрос: какие capabilities обязательны в staging/production и как они
сообщают о недоступности зависимости. Сейчас для будущих локальных проверок доступен
только локальный PostgreSQL; Neon и VPS, по сообщению владельца, недоступны.

## COMPAT — совместимость границ и выпуск

**Принято владельцем:** [общий контракт совместимости и выпуска изменений](../decisions/DEC-20261112-contract-compatibility.md).
Это целевые требования; полное соответствие существующей реализации не проверено.

- COMPAT-1: при изменении API, событий, WebSocket, единиц или смысла полей
  определены потребители; проверены вызывающие сценарии, ошибки и существующие данные.
- COMPAT-2: для несовместимого изменения определены поддерживаемые сочетания версий,
  порядок выпуска, миграция и восстановление при неудаче. Неожиданная поломка
  старого потребителя не считается завершённым переходом.
- COMPAT-3: исходный контракт, реализация и производные файлы согласованы:
  `.proto` проходит генерацию, схемы соответствуют миграциям, модели клиента —
  ответам. Сборка/валидация дополняются проверкой затронутого сценария.

Применимость: backend↔Flutter/Telegram/AI, межсервисные HTTP/gRPC, CDC schemas.
Не обещаем вечную совместимость; breaking change требует плана выпуска.

Проверяемое свойство: «потребитель → изменённый контракт → наблюдаемый результат»
соответствует принятому поведению, включая ошибки и существующее состояние.
При постепенном выпуске проверяются нужные сочетания версий. Период поддержки,
план выпуска и способ восстановления определяет change; новая версия API для
каждой правки и обратимость любой миграции не требуются.

## Как из этого получать работу

Один rollout change выбирает семейство, конкретные операции и потребителей.
В delta spec появляется только принятая и ограниченная по применимости часть
контракта. Например, EXEC-2 для MacroApplier не является доказательством того,
что EXEC-2 уже обеспечен всеми AI tools и webhook consumers.

Edge case — минимальный пример нарушенного свойства с ID и регрессионной проверкой.
Если свойство уже описывает случай, новый requirement не нужен. Если два результата
одинаково допустимы по текущему контракту, уточнение оформляется change/решением.
