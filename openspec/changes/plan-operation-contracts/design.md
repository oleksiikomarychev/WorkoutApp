# Design

## Context

См. [proposal](proposal.md) и [журнал расхождений](../../../docs/development/TEMP-contract-gaps.md).
Применение плана пишет в plans-service и вызывает создание тренировок в workouts-service.
Массовая правка вызывает методы, которые по отдельности фиксируют изменения.
Перенос исключает тренировки с `completed_at`, тогда как массовая правка такого
обязательного фильтра не содержит.

## Goals / Non-Goals

Цель: обеспечить гарантии трёх [delta specs](specs/plan-application/spec.md)
при согласованных пользовательских сценариях. Реализация должна охватывать sync/async
пути и существующих потребителей. Новая модель статусов планов, правила для начатых
тренировок и универсальный движок транзакций в объём не входят.

## Decisions

### Одна граница сохранения массовой правки

Реализованный подход: методы изменения упражнений работают внутри транзакции
вызывающей операции и не делают собственный commit; ошибка любого обязательного
изменения прерывает обход, вызывает rollback и возвращает ошибку. Изменения кэша
публикуются после успешного commit. Это предпочтительнее компенсации после каждого
малого commit: все затронутые упражнения находятся в одной БД workouts-service.
Все действия массовой правки пишут в эту БД; HTTP и worker тесты подтверждают единый rollback.

### Завершённость проверяется до изменения и под защитой от гонки

По [принятому решению](../../../docs/decisions/DEC-20261110-completed-workout-definition.md)
завершённость означает `completed_at IS NOT NULL` или `status == "completed"`.
Обе операции проверяют это для каждой затрагиваемой тренировки и защищают выборку от
конкурирующего завершения до фиксации изменений. Альтернатива — фильтр без защиты
от гонки — может изменить тренировку, завершённую между чтением и commit.

### Повтор применения и межсервисный сбой

По [принятому решению](../../../docs/decisions/DEC-20261110-simple-active-plan-guard.md)
обычный запрос при активном плане отклоняется. Проверку активного плана и создание
нового выполнять под одной пользовательской блокировкой. Сравнение параметров,
ключи и журнал операций не нужны. Явная замена передаётся `replace_active=true`
(по умолчанию `false`) в sync/async запросах. При активном плане без него API
возвращает HTTP 409; async-путь проверяет до постановки задачи и повторно в worker.

Одна транзакция plans-service не охватывает HTTP-создание тренировок. Workouts-service
сохраняет каждый запрос `/generate` одной транзакцией; plans-service отправляет
несколько пакетов. Нужен внутренний идемпотентный endpoint очистки Workout по
`applied_plan_id` и `user_id`, вызываемый при ошибке применения до фиксации плана.
По [решению о начатой тренировке](../../../docs/decisions/DEC-20261112-preserve-started-workout-on-cleanup.md)
он отделяет начатые/завершённые тренировки от неуспешного плана, сохраняя прогресс. При неуспешной очистке
операция остаётся неуспешной и требуется повторное восстановление. По [решению о видимости](../../../docs/decisions/DEC-20261110-temporary-workout-visibility.md)
тренировки сохранённых пакетов могут временно отображаться; при сбое их удаляет
очистка. Отдельное состояние скрытия не вводится.

## Risks / Trade-offs

- Длинная транзакция массовой правки → определить размер допустимой выборки и
  блокировки; проверить конкурирующие изменения.
- Промежуточные тренировки в другом сервисе → не показывать успешный план до
  подтверждения результата; предусмотреть восстановление после перезапуска.
- Явная замена меняет API применения → изучить gateway, agent-service и Flutter-клиент;
  выбрать совместимый переход, прежде чем менять обязательные поля запроса.
- Асинхронные задачи → успешная постановка задачи не равна успеху применения;
  конечный статус должен отражать фактический результат.

## Migration Plan

Сначала добавить проверяемые тесты для текущих расхождений. Затем ввести отказ
при активном плане и явную замену с совместимым переходом клиента, обеспечить
восстановление применения, после этого объединить записи массовой правки в одну
транзакцию и унифицировать фильтр завершённости. Выпускать после тестов sync/async,
сбоев и конкуренции. При откате версии сверить последствия уже частично начатых
применений; точный порядок миграции зависит от выбранной схемы.
