# Design

## Context

См. proposal и [карту](../../../docs/architecture/system-map.md). Текущие три main
specs покрывают часть плановых операций; источники доменных правил, тесты и конфигурация
разнесены по сервисам, docs и клиенту. Изолированный плановый стенд уже существует,
но из его успеха нельзя вывести готовность остальных возможностей.

## Goals / Non-Goals

Цель — связать обзор приложения с ограниченными changes и проверками свойств.
Не меняются runtime/API/DB/CI; этот docs/config change использует `skip_specs: true`.
Продуктовые решения остаются в draft до обсуждения.

## Decisions

### Карта и доказательства отдельно от нормативных требований

Карта хранит наблюдения, источники и неизвестное. Main specs продолжают описывать
согласованное поведение в проверенной области. Альтернатива — записать желаемые
глобальные SHALL прямо в main — создала бы ложную видимость соответствия сервисов.

### Семейства контрактов и постепенное расширение применимости

Шесть семейств служат вопросами к change. У каждого есть свойство, границы и тип
проверки. Rollout выбирает конкретные операции и потребителей; следующая итерация
расширяет requirement через delta. Это избегает отдельной новой spec для каждого
частного значения и одновременно не обещает глобальной атомарности/идемпотентности.

### Короткий анализ влияния вместо повторного общего аудита

AGENTS.md и OpenSpec config дают ссылки на карту и минимальную запись влияния.
Полный каталог не инлайнится в context. Для локального fix без изменения контракта
сохраняется лёгкий путь. Custom schema и новые внешние инструменты не требуются.

### Будущие проверки остаются отдельными changes

Карта не является автоматически вычисленной зависимостью, а config не является
CI enforcement. Изоляция тестов и обязательные gates предложены отдельно, потому
что найденные suite могут использовать импортированные application session factories.
Произвольный запуск всех тестов в обычном окружении здесь не выполняется.

## Risks / Trade-offs

- Устаревание карты → обновлять затронутую область вместе с change, указывать дату/источник.
- Общее правило не подходит модулю → определить применимость и принятую альтернативу;
  не превращать исключение в молчаливую деградацию.
- Draft принимается за действующий контракт → статус предложения в каталоге и config;
  новые main specs этим change не создаются.
- Разрастание процесса → короткая запись для малых изменений; шесть вопросов
  не требуют шесть отдельных документов или согласований на каждую задачу.

## Verification

Проверить относительные ссылки и существование указанных исходных файлов, валидность
config текущим CLI, отсутствие новых runtime-specs, чтение правил proposal/design/tasks
и apply, затем `openspec validate --all --strict --no-interactive` и `git diff --check`.
Никакие результаты нового широкого test/deployment аудита не заявляются.
