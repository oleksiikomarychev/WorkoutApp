# Adaptive Personalized RPE Engine: план без обучающих данных

> Статус: проектный архитектурный план, обновлён 20.10.2026. Приложение ещё не выпущено и проверенных тренировочных наблюдений нет. Описанные миграции, API и персонализация пока не реализованы.

## Цель и исходное состояние

В день запуска все расчёты выполняются по существующей [`rpe_table.json`](rpe_table.json). Сервис собирает отдельно подтверждённое пользователем усилие после подхода. Лишь когда качественных данных достаточно, появляется персональная кривая для конкретного упражнения. Обучение общей модели по пользователям — отдельный будущий этап.

Аудит кода, от которого зависит план:

- [`rpe_service/calculation.py`](rpe_service/calculation.py) читает таблицу, а [`rpe_service/rpe_calculations.py`](rpe_service/rpe_calculations.py) округляет дробный RPE до целого. Таблица уже работает и должна оставаться источником холодного старта.
- [`workout_detail_screen.dart`](../../flutter_app/lib/screens/workout_detail_screen.dart) автоматически подставляет RPE по весу и повторам. Источник числа не сохраняется. При обновлении экран меняет `updatedSet.rpe`, но передаёт в сервис `updatedSet.effort`; сквозное сохранение полей требует проверки и исправления.
- Редактор Flutter обращается к `/exercises/instances/{id}/sets/{id}` через Gateway, где маршрут ведёт в `exercises-service` без нужного endpoint. Реальный владелец редактирования — `workouts-service` (`/workouts/instances/{id}/sets/{id}`), который ожидает `volume/working_weight/effort/order_index`, тогда как Flutter отправляет `reps/weight/rpe/order`. Исправление маршрута, схемы и отправляемого `effort` — первый блокер сбора данных.
- В [`workouts-service/workouts_service/models.py`](../workouts-service/workouts_service/models.py) `workout_sets.effort` — единственное поле RPE подхода. Выполнение отмечается отдельно в `workout_sessions.progress.completed`. Строка `workout_sets` изменяема и не является неизменяемым фактом сессии.
- В [`user-max-service/user_max_service/models.py`](../user-max-service/user_max_service/models.py) есть `true_1rm`, `verified_1rm` и `source`, но `true_1rm` может быть результатом формулы Epley. Наличие числа не подтверждает его независимость и точность.
- CDC переносит `workout_sets` и `workout_sessions`. Текущая [`analytics.fact_workout_sets`](../../analytics/clickhouse/init/10_analytics_views.sql) содержит `effort` без источника и подтверждения выполнения. Историческую витрину нельзя использовать как размеченный датасет.

## Стадии продукта

| Стадия | Условие | Что получает пользователь |
| --- | --- | --- |
| Cold Start | Нет пригодных наблюдений или оценка силы ненадёжна | Исходная RPE-таблица |
| Calibration | Есть подтверждённые подходы, но персональная кривая ещё неопределённа | Таблица; индивидуальный расчёт только в теневом режиме |
| Personalized RPE | Неопределённость ограничена и проверка на более поздних тренировках показала пользу | Версионированный профиль упражнения с откатом к таблице |
| Population Learning | Данные многих атлетов позволяют проверить общий профиль | Улучшенный начальный профиль; персональная калибровка сохраняется |

Переход определяется информацией в данных, а не одним числом подходов. У одного пользователя может работать персональная сетка жима и таблица для нового упражнения.

## Компоненты и ответственность

```text
Flutter ──► Gateway ──► workouts-service ──► PostgreSQL workout_set_observations
   │                         │                         │
   │                         │                 Debezium → Kafka → ClickHouse
   │                         │                               │
   │                         │                      пригодный временной срез
   │                         │                               │
   │                         └───────────► calibration job ◄──┘
   │                                           │
   │                                PostgreSQL profile/grid versions
   │                                           │
   └── Gateway ──► rpe-service ◄───────────────┘
                     │
               rpe_table.json — обязательный fallback
```

| Компонент | Граница ответственности |
| --- | --- |
| Flutter | Показать цель и прогноз отдельно; принять необязательный ответ после выполнения; сохранить локальную операцию до подтверждения сервера. |
| Gateway | Передать проверенный контекст пользователя; сохранить совместимость существующих маршрутов; не принимать `user_id` из запроса клиента. |
| `workouts-service` | Владеть фактом выполненного подхода и его изменениями; проверять связь с сессией, подходом и пользователем. |
| Analytics | Реплицировать факты и собрать воспроизводимый срез. Витрины не являются источником истины для сохранения ответа. |
| `user-max-service` | Предоставить оценку силы с источником и датой; не объявлять расчёт по RPE независимым измерением. |
| `rpe-service` | Выполнять табличный и персональный расчёт, выбирать действующую версию профиля, возвращать происхождение результата. |
| Calibration job | Подгонять параметры вне запроса пользователя, проверять качество, публиковать версию или оставлять таблицу. |

Синхронный расчёт в `rpe-service` не должен ждать ClickHouse или оптимизатор. CDC и калибровка могут отставать: это задержит обновление персонального профиля, но не сломает расчёт. До первого релиза обязательны работающий маршрут редактирования, табличный расчёт на сервере и офлайн, корректная запись наблюдений и проверяемый путь данных через CDC. Математическое ядро и схемы версий можно подготовить до релиза; включать персональную выдачу без реальных проверенных данных нельзя.

## Данные: разделить план, прогноз и факт

Для фактически выполненного подхода сохранять три независимых значения:

```json
{
  "workout_session_id": 901,
  "workout_set_id": 49201,
  "exercise_id": 12,
  "completed_at": "2026-10-20T10:15:30Z",
  "weight_completed": 80.0,
  "reps_completed": 8,
  "target_rpe": 8.0,
  "predicted_rpe": 8.0,
  "prediction_source": "default_table",
  "prediction_version": "rpe-table-v1",
  "actual_rpe": 8.5,
  "actual_rpe_source": "user_reported",
  "feedback_method": "independent_entry",
  "rpe_confirmed_at": "2026-10-20T10:15:45Z"
}
```

`target_rpe` — цель программы; `predicted_rpe` — показанный приложением расчёт; `actual_rpe` — **явно сообщённое ощущение после подхода**. Отметка «выполнено», автоматически заполненное поле и сохранение формы без действия пользователя не превращают прогноз в `user_reported`. Сначала спрашивать RPE без раскрытия прогноза: это `feedback_method=independent_entry`. Если интерфейс предлагает подтвердить показанное число, сохранять `confirmed_suggestion` отдельно: это ответ пользователя, но он подвержен эффекту якоря и не равен независимой метке при калибровке/валидации. При пропуске `actual_rpe`, `actual_rpe_source`, `feedback_method` и время подтверждения остаются `null`. Старым данным нельзя задним числом присвоить `user_reported`.

Сначала восстановить работающий маршрут редактирования подхода Flutter → Gateway → `workouts-service` и согласовать карту `reps`/`volume`, `weight`/`working_weight`, `rpe`/`effort`, `order`/`order_index`. Исправить отправку изменённого `rpe` вместо старого `effort`; интеграционный тест должен записать подход через клиентский API и прочитать те же значения обратно. Существующий `workout_sets.effort` считать плановым или расчётным параметром для совместимости, а не фактическим RPE пользователя.

### Запись наблюдения в PostgreSQL

Добавить в `workouts-service` таблицу **`workout_set_observations`** с уникальным ключом `(workout_session_id, workout_set_id)`. Хранить `user_id`, упражнение, снимок фактических веса и повторов, время выполнения, цель, прогноз, версию прогноза, необязательный подтверждённый RPE и время подтверждения, статус отмены/исправления. Это запись конкретной сессии: последующее редактирование `workout_sets` не меняет прошлый факт.

Предлагаемый контракт миграции Alembic (типы и ограничения уточняются при реализации):

```sql
CREATE TABLE workout_set_observations (
    id                  BIGSERIAL PRIMARY KEY,
    workout_session_id  INTEGER NOT NULL REFERENCES workout_sessions(id) ON DELETE CASCADE,
    workout_set_id      INTEGER NOT NULL,
    user_id             VARCHAR(255) NOT NULL,
    exercise_id         INTEGER NOT NULL,
    completed           BOOLEAN NOT NULL DEFAULT TRUE,
    completed_at        TIMESTAMPTZ,
    weight_completed    NUMERIC(9, 2),
    reps_completed      INTEGER,
    target_rpe          NUMERIC(3, 1),
    predicted_rpe       NUMERIC(3, 1),
    prediction_source   VARCHAR(32),
    prediction_version  VARCHAR(64),
    actual_rpe          NUMERIC(3, 1),
    actual_rpe_source   VARCHAR(32),
    feedback_method     VARCHAR(32),
    rpe_confirmed_at    TIMESTAMPTZ,
    measurement_source  VARCHAR(32) NOT NULL DEFAULT 'unknown',
    revision            INTEGER NOT NULL DEFAULT 1,
    updated_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (workout_session_id, workout_set_id),
    CHECK (reps_completed IS NULL OR reps_completed > 0),
    CHECK (weight_completed IS NULL OR weight_completed > 0),
    CHECK (actual_rpe IS NULL OR
           (actual_rpe BETWEEN 1 AND 10 AND actual_rpe * 2 = trunc(actual_rpe * 2))),
    CHECK (measurement_source IN ('client_measured', 'server_set_snapshot', 'imported', 'unknown')),
    CHECK ((actual_rpe IS NULL AND actual_rpe_source IS NULL AND feedback_method IS NULL AND rpe_confirmed_at IS NULL)
        OR (actual_rpe IS NOT NULL AND actual_rpe_source = 'user_reported'
            AND feedback_method IN ('independent_entry', 'confirmed_suggestion')
            AND rpe_confirmed_at IS NOT NULL))
);
CREATE INDEX ix_rpe_observations_user_exercise_time
    ON workout_set_observations (user_id, exercise_id, completed_at);
CREATE TABLE workout_observation_operations (
    user_id          VARCHAR(255) NOT NULL,
    operation_id     UUID NOT NULL,
    observation_id   BIGINT REFERENCES workout_set_observations(id) ON DELETE CASCADE,
    response_revision INTEGER NOT NULL,
    response_body    JSONB NOT NULL,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, operation_id)
);
```

`workout_set_id` сохраняется как идентификатор снимка без каскадного FK на изменяемую/удаляемую строку `workout_sets`: исторический факт переживает удаление шаблонного подхода. При удалении аккаунта наблюдения удаляются вместе с сессией. `revision` увеличивается транзакционно при каждом содержательном изменении; `operation_id` сохраняется отдельно для идемпотентности. Завершённый подход без измеренных веса/повторов можно хранить для UI, но он не попадает в калибровку. Снимок из плановой строки (`server_set_snapshot`) не приравнивается к измерению клиента; импорт Hevy получает `imported` или `unknown`, никогда `user_reported` без явного подтверждения в этом приложении.

API должен проверять принадлежность сессии и подхода пользователю на сервере и атомарно связывать наблюдение с выполнением. `user_id` брать из аутентификации. Все пути изменения выполнения (`update_progress`, completion одного подхода, complete-all и импорт Hevy) вызывают один доменный метод изменения факта. Он блокирует строку сессии (`SELECT ... FOR UPDATE`) либо использует нормализованное состояние и меняет `progress.completed` и наблюдение в одной транзакции; read-modify-write JSON без блокировки теряет конкурентные изменения. Отмена исключает факт из калибровки; исправление повышает `revision`. Для офлайн-очереди сервер хранит `(user_id, operation_id)` и ответ операции, повтор отдаёт тот же результат, а новая операция требует `expected_revision`/CAS. Конфликт устаревшей правки возвращает текущую ревизию и не перезаписывает более свежий ответ.

После выбранного рабочего подхода Flutter показывает необязательный вопрос о **фактическом** RPE с шагом 0.5 до раскрытия прогноза; можно ответить или пропустить. Если применяется подтверждение подсказки, метод ответа сохраняется отдельно. Выполнение подхода сохраняется и при пропуске; поздняя правка ответа должна быть возможна.

### CDC и аналитика

После миграции PostgreSQL добавить таблицу наблюдений в publication и Debezium `table.include.list`, создать raw-слой и `analytics.fact_rpe_observations` в ClickHouse. Проверить вставку, изменение и отмену на реальном CDC-пути. В витрине сохранить источник RPE, версию прогноза, факт выполнения и время изменения; повторные события не должны удваивать подход. Срез обучения фиксировать по времени: будущие правки и будущие оценки силы не попадают в прошлое.

Порядок схемы: Alembic `workouts-service` → `ALTER PUBLICATION debezium_workouts ADD TABLE workout_set_observations` для уже созданной publication → обновление `workouts-connector.json` → новая `raw.workout_set_observations` и Kafka-таблица/MV → витрина. При чистом развёртывании обновить и исходный SQL publication. Для уже работающего ClickHouse использовать отдельную миграцию: повторный `CREATE TABLE IF NOT EXISTS` не добавит новые колонки.

В raw-слое хранить все поля наблюдения, `__op`, `__source_ts_ms` и `revision`. В актуальной витрине ключом остаётся `id` наблюдения; при исправлении брать максимальную `revision`, а `completed=false` исключать из обучающего среза. Текущий ClickHouse использует `__source_ts_ms` как версию, поэтому равные миллисекунды не задают порядок: для новой витрины нужен порядок по транзакционной `revision` с явным детерминированным разрешением дублей. Проверить replay, равные timestamps, delete tombstones и передачу PostgreSQL `NUMERIC` через JSON/CDC. `fact_workout_sets` и `fact_workout_progress` остаются существующими витринами без подмены `effort`.

Текущий `ReplacingMergeTree` хранит актуальное состояние, но после схлопывания версий не гарантирует воспроизведение прежнего обучающего среза. Поэтому calibration job перед подгонкой материализует список `(observation_id, revision, max_source_id, max_version)`, фактические признаки, значения и происхождение силы, версии таблицы/правил и метки в неизменяемый snapshot с хэшем. `dataset_snapshot_id` в журнале указывает именно на этот snapshot, а `data_cutoff_at` ограничивает допустимые события. Простого запроса к текущей `FINAL`-витрине для воспроизводимости недостаточно.

Фильтр калибровки: `completed=true`, `actual_rpe_source='user_reported'`, пригодный `feedback_method`, измеренные вес/повторы/время и подходящий источник силы. Независимый ввод и подтверждение подсказки анализировать раздельно; подтверждения не должны единолично доказывать улучшение. Разминку и область RPE, где модель плохо идентифицируется, отсекать по версионированным правилам. Дедупликация по наблюдению и `revision`; срез строить с `data_cutoff_at`, а не по текущему состоянию всех таблиц.

Текущие `fact_workout_sets.effort` и `fact_workout_progress.actual_effort` нельзя считать метками пользователя. Инфраструктура и порядок изменения схем описаны также в [`analytics/README.md`](../../analytics/README.md).

## Математическое ядро

Возможная параметрическая форма выносливости:

$$N_{\max}(I;k)=1+k\left(\frac{100}{I}-1\right),\qquad I=100\frac{w}{S},\qquad N_{\mathrm{pred}}=N_{\max}(I;k)-(10-r).$$

Здесь `w` — вес подхода, `S` — оценка 1RM **на дату подхода**, `r` — подтверждённый RPE. При 80% 1RM и RPE 10 таблица даёт 8 повторов, откуда локально `k=28`. Подгонка по строке RPE 10 в диапазоне 70–95% даёт около `k₀=28.2` и непрерывную ошибку около 0.38 повтора внутри этого диапазона, но около 53% расхождение может доходить примерно до трёх повторов. Это локальная аппроксимация таблицы, а не обученная физиология; перед реализацией зафиксировать диапазон, веса ячеек и версию таблицы. Экстраполяция поправки ниже проверенного диапазона запрещена.

При нуле наблюдений использовать **сам JSON**: одна параметрическая кривая не воспроизводит все его ячейки. Каноническое непрерывное ядро для поддерживаемой области: `F(I,r;k,g)=(1−g)T(I,r)+g P(I,r;k)`, где `T` — монотонная интерполяция между соседними **доступными** узлами исходной таблицы, `P=1+k(100/I−1)−(10−r)`, `0≤g≤1`; `g=0` воспроизводит исходные узлы таблицы точно. Версия интерполяции, таблицы и область применения фиксируются контрактом; пробелы между недоступными ячейками не заполняются. За пределами проверенной области персонализации используется таблица. Для дробного RPE ключи сетки — `rpe_x2`: 8.5 → 17. `g` отражает допуск персонализации по неопределённости, а не автоматически растёт с числом подходов.

Если доступна независимая оценка `S`, индивидуальный `k` можно найти ограниченной робастной оптимизацией с регуляризацией к `k₀`:

$$k^*=\arg\min_{k\in[k_{\min},k_{\max}]}\sum_i w_i\rho\left(F(I_i,r_i;k,1)-N_{\mathrm{completed},i}\right)+\lambda(k-k_0)^2.$$

Вес `w_i` отражает качество записи и неопределённость силы; `ρ` ограничивает влияние выбросов. Кандидат `k` оценивается без подмены табличного baseline; опубликованный прогноз использует только `F` с зафиксированным `g`. Достаточность оценивать по разнообразию нагрузок, повторов и дат, согласованности наблюдений и ширине прогностического интервала. Формальное правило публикации и выбор `g` зафиксировать до оценки первых пользовательских данных; численные пороги менять только через версионированное инженерное решение.

1RM, вычисленный из того же подхода по старой RPE-таблице, не является независимым якорем. Для прямого проверенного 1RM хранить источник, время и неопределённость. При неизвестном `S` сначала оценивать силу отдельно; совместно оценивать `S` и `k` можно лишь при достаточном разнообразии нагрузок и проверенной идентифицируемости. До этого персональный профиль не публиковать. Epley-оценку не приравнивать к прямому тесту 1RM.

Генератор персональной сетки проверяет монотонность и доступность ячеек, хранит версию формулы. При отсутствии, устаревании или отклонении профиля сервис возвращает исходную таблицу.

### Прямой и обратные расчёты

Для непрерывного ядра три сценария используют **одну функцию `F` и один набор параметров**. Закрытые обратные формулы чистой `P` неприменимы к смеси `T/P` и здесь не используются:

| Известно | Вычисляется | Формула до дискретизации |
| --- | --- | --- |
| `I`, `r` | `n` | `n_raw = F(I,r;k,g)` |
| `n`, `r` | `I` | Найти `F(I,r;k,g)=n` ограниченным поиском по поддерживаемому интервалу `I` |
| `I`, `n` | `r` | Найти `F(I,r;k,g)=n` ограниченным поиском по поддерживаемому интервалу `r` |

Допустимая область задаётся явно: `I` в пределах поддерживаемой таблицы и опубликованного профиля, `r` в пределах ячеек таблицы, `n ≥ 1`, `S > 0`; ячейка с `n_raw < 1` отсутствует. Округление повторов и веса применять после вычисления непрерывного значения. Пример: 95% 1RM при RPE 5 не становится искусственно «1 повтором». Для табличного режима область определяется реально существующими ячейками JSON: в нём RPE от 4 до 10 и нет половинных значений; дробные значения возможны лишь внутри интерполируемых интервалов.

Округление и плато создают коллизии: нескольким интенсивностям или RPE может соответствовать одно число повторов. Численный поиск ведётся на непрерывной `F`; если решения нет в доступной области, вернуть `unavailable`, если решений интервал — вернуть диапазон/`ambiguous` и детерминированное правило представления. Не выбирать произвольно меньший RPE как «безопасный»: это может занизить ощущаемую тяжесть. Существующий контракт и его nearest-match поведение менять только с версионированием, чтобы не сломать клиентов.

### Источник 1RM и отделение силы от формы кривой

Состояние пользователя по упражнению на момент `t` разделяется на `S(user, exercise, t)` — силу — и `k(user, exercise, t)` — форму зависимости повторов от интенсивности. Контракт `user-max-service` должен возвращать `value`, `exercise_id`, `measured_at/effective_at`, `available_at`, `source`, `uncertainty`, `estimate_version` и идентификаторы входных подходов. Срез выбирает только значение, действовавшее **и доступное** на дату подхода. Позднее измерение нельзя присоединять к раннему подходу. Сейчас `rpe-service` по `user_max_id` получает только число; этот RPC надо расширить до калибровки. `verified_1rm` в текущей базе и `true_1rm` по Epley не дают автоматически метку «прямой тест»; источник нужно нормализовать в `user-max-service`.

Источники для будущего контракта: `tested_1rm`, `independent_estimate`, `rpe_derived`, `unknown`. `rpe_derived` из того же подхода/таблицы исключается из подгонки `k`; зависимости входных подходов проверяются по их ID. Для `independent_estimate` учитывается неопределённость и возможная ошибка от времени. Если сила неизвестна, нужен отдельный оценщик силы с неопределённостью либо совместная оценка `S,k`: разнообразные нагрузки/сессии, проверка ранга/идентифицируемости, интервалы параметров и проверка на последующих сессиях. До выполнения этих условий используется таблица, но отсутствие прямого теста 1RM не должно навсегда закрывать персонализацию.

### Алгоритм калибровки и допуск к публикации

1. Сформировать неизменяемый срез с идентификаторами наблюдений и версиями правок, границей времени, правилами фильтрации, версиями таблицы и оценок силы.
2. Оценить начальное `k₀` из выбранного диапазона исходной таблицы; хранить его рядом с версией формулы. Ограничение `k ∈ [15, 45]` из первоначального проекта считать рабочей инженерной гипотезой, которую надо проверить на монотонность и граничные случаи.
3. Для каждого `(user_id, exercise_id)` решать робастную задачу с регуляризацией к `k₀`. В SciPy подойдёт ограниченный `least_squares` с явной обработкой веса, выбросов и коэффициента регуляризации. Независимость соседних подходов одной сессии не предполагать.
4. Оценивать неопределённость по тренировкам/сессиям, а не по отдельным подходам; проверять разнообразие интенсивностей и устойчивость `k` при исключении одной сессии. Противоречивые данные увеличивают интервал и удерживают таблицу.
5. Сравнивать прогноз с исходной таблицей на более поздних сессиях без утечки будущего. Логировать MAE по RPE и/или повторам вместе с числом и диапазоном пригодных наблюдений, интервалом и долей недоступных ячеек. Правило публикации версионировать **до** использования наблюдений: покрытие разных интенсивностей и сессий, источник/неопределённость силы, верхняя граница ошибки RPE на области применения, улучшение относительно таблицы на будущих сессиях и ограничение вреда по подгруппам/краям диапазона. Неопределённую оценку и малую контрольную выборку оставлять в теневом режиме; вне доказанной области применять таблицу. Числа порогов назначить инженерно до запуска калибровки и хранить с `policy_version`.

При нуле наблюдений математически проверяются точность аппроксимации таблицы, монотонность, инверсия, границы и производительность. Реальную ошибку RPE, включая цель `MAE ≤ 0.4`, до появления подтверждённых ответов вычислить нельзя. Синтетические данные подходят для проверки кода и деградации при шуме, но не доказывают качество персонализации.

## Хранение профилей и версий сеток

Эти таблицы нужны, когда появятся кандидаты для персональной выдачи. Их можно мигрировать заранее, оставив пустыми. Фрагмент схемы:

```sql
CREATE TABLE rpe_model_profiles (
    id                 BIGSERIAL PRIMARY KEY,
    user_id            VARCHAR(255) NOT NULL,
    scope              VARCHAR(32) NOT NULL, -- EXERCISE; будущие GLOBAL/MOVEMENT_PATTERN
    scope_id           VARCHAR(64),
    active_version_id  BIGINT, -- FK на версии добавляется после создания обеих таблиц
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    CHECK (scope IN ('EXERCISE', 'GLOBAL', 'MOVEMENT_PATTERN')),
    CHECK ((scope = 'GLOBAL' AND scope_id IS NULL)
        OR (scope <> 'GLOBAL' AND scope_id IS NOT NULL))
);
CREATE UNIQUE INDEX uq_rpe_profile_global
    ON rpe_model_profiles (user_id) WHERE scope = 'GLOBAL';
CREATE UNIQUE INDEX uq_rpe_profile_scoped
    ON rpe_model_profiles (user_id, scope, scope_id) WHERE scope <> 'GLOBAL';

CREATE TABLE rpe_profile_versions (
    id                           BIGSERIAL PRIMARY KEY,
    profile_id                   BIGINT NOT NULL REFERENCES rpe_model_profiles(id) ON DELETE CASCADE,
    version                      INTEGER NOT NULL,
    k_factor                     DOUBLE PRECISION NOT NULL,
    blend_g                      DOUBLE PRECISION NOT NULL,
    applicability                JSONB NOT NULL, -- допустимые I/r и политика fallback
    prediction_interval_90_width DOUBLE PRECISION,
    sample_count                 INTEGER NOT NULL,
    model_version                VARCHAR(64) NOT NULL,
    source_table_version         VARCHAR(64) NOT NULL,
    source_table_hash            VARCHAR(128) NOT NULL,
    policy_version               VARCHAR(64) NOT NULL,
    dataset_snapshot_id          VARCHAR(128) NOT NULL,
    data_cutoff_at               TIMESTAMPTZ NOT NULL,
    status                       VARCHAR(20) NOT NULL, -- SHADOW / ELIGIBLE / REJECTED
    grid                         JSONB NOT NULL,
    grid_hash                    VARCHAR(128) NOT NULL,
    diagnostics                  JSONB NOT NULL,
    created_at                   TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (profile_id, version),
    UNIQUE (profile_id, id),
    CHECK (blend_g BETWEEN 0 AND 1),
    CHECK (sample_count >= 0)
);
ALTER TABLE rpe_model_profiles
    ADD CONSTRAINT fk_active_profile_version
    FOREIGN KEY (id, active_version_id) REFERENCES rpe_profile_versions(profile_id, id);

CREATE TABLE rpe_training_runs (
    id                  BIGSERIAL PRIMARY KEY,
    run_uuid            UUID NOT NULL UNIQUE,
    dataset_snapshot_id VARCHAR(128) NOT NULL,
    model_version       VARCHAR(64) NOT NULL,
    policy_version      VARCHAR(64) NOT NULL,
    data_cutoff_at      TIMESTAMPTZ NOT NULL,
    profiles_updated    INTEGER NOT NULL DEFAULT 0,
    train_reps_mae      DOUBLE PRECISION,
    val_reps_mae        DOUBLE PRECISION,
    status              VARCHAR(20) NOT NULL,
    diagnostics         JSONB,
    executed_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Уникальные частичные индексы исключают дубли глобального и scoped-профиля при `NULL` в `scope_id`. Каждая версия — неизменяемый комплект параметров, области, неопределённости, snapshot и сетки; статус проверки лучше фиксировать отдельным журналом, если он меняется после создания. FK гарантирует, что активный указатель ведёт к версии **того же** профиля. Дополнительно сервис проверяет `scope_id` для упражнения, конечность `k_factor`, границы и монотонность сетки, идентичность пользователя и полноту диагностик. `sample_count` — диагностический показатель, а не единственное условие включения. В JSONB ключи усилия кодируются как `rpe_x2`, например `{ "80": { "17": 6, "18": 6 } }`; при чтении клиент знает диапазон интенсивности, шаг и версию формулы.

Публикация одной версии — транзакция PostgreSQL: заблокировать identity-профиль, проверить неизменяемую версию и сетку, сменить `active_version_id`, записать журнал. Откат возвращает указатель на прежнюю **полную** версию, включая `k`, `g` и область. Для первого варианта читать активный указатель из PostgreSQL на каждый запрос, а Redis отложить. Если кэш понадобится, хранить только сетку под версионированным ключом `(user_id, exercise_id, version)`; активный указатель всегда читать из БД либо снабжать строго ограниченным TTL. Сбой инвалидации не должен оставлять старую активную версию дольше документированного TTL; при требовании немедленного отката кэш указателя запрещён. На промахе/ошибке Redis читать БД, при отсутствии валидной версии возвращать таблицу. Проверять откат при конкурентных чтениях.

## API и совместимость

### Сохранение выполненного подхода

Расширить существующий `PUT /sessions/{session_id}/instances/{instance_id}/sets/{set_id}/completion`: при `completed=true` он создаёт или обновляет наблюдение и снимает фактические вес/повторы в той же транзакции, что и `progress.completed`. Для старых клиентов сервер может брать числа из текущего подхода, но отмечает `server_set_snapshot` и не использует его для обучения. Новые клиенты передают измеренные числа, `operation_id`, `expected_revision` и версию показанного прогноза. `completed=false` деактивирует наблюдение; восстановление того же подхода повышает `revision`. `update_progress`, complete-all и Hevy import проходят через тот же доменный метод; у импорта источник `imported/unknown`, не `user_reported`.

Отдельный `PATCH /sessions/{session_id}/instances/{instance_id}/sets/{set_id}/rpe-feedback` принимает `{ "actual_rpe": 8.5, "feedback_method": "independent_entry", "operation_id": "…", "expected_revision": 3 }` после завершения и записывает `actual_rpe_source='user_reported'` сервером. Запрос с явным удалением ответа очищает значение, метод и источник. Ответ содержит текущую `revision`. Клиент повторяет тот же `operation_id` после потери сети; новый ключ со старой `expected_revision` получает конфликт и текущую ревизию, а не затирает более позднюю запись. Сервер проверяет владельца и завершённость подхода. Изменение поля RPE в плановом редакторе не вызывает этот endpoint и не создаёт обучающую метку.

### Расчёт и получение сетки

В [`proto/rpe.proto`](../../proto/rpe.proto) сохранить номера полей запроса 1–8 и ответа 1–3. Возможное аддитивное расширение: `exercise_id=9`, `calculation_mode=10`; в ответе `intensity=4`, `effort=5`, `volume=6`, `model_source=7`, `grid_version=8`, `combination_available=9`, `predicted_reps_raw=10`. Изменение схемы требует регенерации stubs у `rpe-service`, Gateway и остальных вызывающих сервисов, плюс тестов совместимости старого клиента.

Сейчас gRPC `Compute` возвращает фактически только вес и сообщение, хотя HTTP внутри сервиса умеет возвращать все три параметра; Gateway `/api/v1/rpe/compute` тоже отдаёт только вес. Это следует выровнять до подключения персональных сеток, не меняя существующие поля ответа. Ошибку невозможной комбинации выражать отдельным кодом/флагом, а не ближайшей заведомо неверной ячейкой в новом строгом режиме. Для старых запросов оставить прежнюю семантику или явно включать `FALLBACK_OK`; `STRICT` нужен для новых вычислений и тестов.

`GET /api/v1/rpe/my-grid?exercise_id=12` возвращает сетку, источник (`default`/`user_exercise`), версию, ограничения и время актуальности. `user_id` извлекается из `request.state.user.uid` проверенного middleware Gateway; сейчас `/rpe/compute` берёт клиентский `X-User-Id`, и это надо исправить **до** персонального compute. Тест с подменённым заголовком должен доказать, что персональные данные и профиль чужого пользователя недоступны. Внутренний вызов передаёт доверенный UID по защищённому сервисному каналу. Flutter кэширует сетку под `(user_id, exercise_id, version)` и очищает персональный кэш при выходе/смене аккаунта. При пустом кэше использует локальный версионированный asset таблицы.

Локальная Flutter-таблица сейчас имеет дополнительные 121 ячейку RPE 1–3 относительно серверной, а экран при ошибке загрузки оставляет `_rpeTable={}`. Перед выпуском выбрать единый канонический диапазон и asset/hash, автоматически сравнивать общие и дополнительные ячейки при сборке, а при сетевой ошибке загружать локальную таблицу. Офлайн-расчёт и отображение недоступных ячеек должны совпадать с контрактом сервера.

## Инструменты по моменту применения

| Компонент | Когда нужен | Роль |
| --- | --- | --- |
| Существующая таблица, Python и текущий сервис | Сразу | Холодный старт, совместимость и fallback. |
| PostgreSQL + Alembic | До релиза для наблюдений; позднее для профилей | Источник фактов, версии и атомарная публикация. |
| Debezium, Kafka, ClickHouse | До релиза для нового факта | Репликация и воспроизводимые срезы; текущая инфраструктура уже существует. |
| SciPy | После первых пригодных наблюдений | Ограниченная робастная оптимизация персонального коэффициента. |
| Фоновый job / Celery | Когда пересчёт станет регулярным | Вынести калибровку из пути запроса; не обязателен для пустого датасета. |
| Redis | При подтверждённой потребности в кэше сеток | Ускорить чтение активной версии с контролем инвалидации. |
| PyMC, PyTorch, MLflow, RL-инструменты | Только по отдельному техническому обоснованию и данным | Общий prior, более сложные модели или управление нагрузкой. |

Контекстный бандит/RL относится к выбору действия между подходами, а не к восстановлению RPE-сетки. Для его честной оценки потребуются отдельные логи предложенного действия, вероятности выбора и результата. До появления таких логов RL не включается в критический путь.

## Отложенные архитектурные расширения

Общую модель можно поставить над персональной регуляризацией: `k_user,exercise` тянется к профилю упражнения и затем к общему prior. PyMC или другой иерархический инструмент имеет смысл лишь если простая калибровка на данных многих пользователей систематически проигрывает и есть достаточное покрытие упражнений. Второй коэффициент кривой (`alpha_factor` в исходном плане) не стоит добавлять до проверки идентифицируемости: два свободных параметра на редких и однотипных подходах дают видимость персонализации без устойчивого прогноза. Выбор новой модели фиксируется новой `model_version`, новым snapshot и сравнением с таблицей и однопараметрической моделью.

Коррекция веса между подходами — другой контракт. Если когда-нибудь появится политика действий, для каждого предложения нужно сохранять доступные варианты веса, выбранное действие, вероятность его выбора, версию политики, контекст и наблюдаемый результат. Без вероятности действия исторический лог не подходит для корректной off-policy оценки. Детерминированные ограничения изменения нагрузки и реакцию на RPE 10 следует проектировать и тестировать отдельно от обучаемой политики; предложенные ранее пределы вроде 5% за шаг являются гипотезами, а не текущим правилом приложения. Анализ текстовых заметок или Jev не является зависимостью RPE Engine.

- [ ] Ввести метрики `observations_total`, `user_reported_share`, `eligible_share` и причины отбраковки по упражнению и источнику силы. При нуле данных все счётчики корректно равны нулю.

### Этап 3. Математика и совместимость до релиза

- [ ] Зафиксировать единый asset/hash `rpe_table.json` и Flutter-таблицы, допустимый диапазон и допуски для `k₀`; гарантировать загрузку локальной таблицы при сетевой ошибке и очистку персонального офлайн-кэша при выходе.
- [ ] Выделить чистое математическое ядро, генератор сетки и валидатор монотонности; проверить `n_raw < 1`, границы `I=100`, дробный RPE и невозможные комбинации.
- [ ] Протестировать три направления расчёта, коллизии после округления, режимы `STRICT`/`FALLBACK_OK`, обратную совместимость HTTP/gRPC и локальную таблицу Flutter.
- [ ] Измерить задержку табличного расчёта и поведение при отключённых PostgreSQL/ClickHouse/Redis. Табличный ответ должен оставаться доступным.

### Этап 4. Калибровка после появления пригодных данных

- [ ] Расширить as-of контракт `user-max-service` значением, источником, неопределённостью, временем доступности и зависимыми подходами; отклонять циклические и будущие оценки. Для неизвестной силы проверить отдельную или совместную оценку `S,k` и идентифицируемость; до её проверки оставлять таблицу.
- [ ] Подключить SciPy и фоновый запуск. Версионировать параметры оптимизации, обучающий срез и диагностические показатели.
- [ ] Считать неопределённость по сессиям, разнообразие нагрузок и расхождение наблюдений; сравнивать с таблицей на последующих сессиях.
- [ ] Сохранять теневые профили и причины отказа. Пока правило допуска не выполнено, сервер возвращает таблицу.

### Этап 5. Публикация и эксплуатация персональных сеток

- [ ] Создать таблицы профилей, версий сеток и запусков; добавить авторизованный endpoint получения своей сетки и совместимое расширение protobuf.
- [ ] Реализовать транзакционную публикацию и откат **полной** неизменяемой версии; сначала читать активный указатель из PostgreSQL, вводить Redis только с измеренной необходимостью и заданной максимальной задержкой отката. Проверить конкурентные публикации и отсутствие доступа к сетке другого пользователя.
- [ ] Переключать только конкретные упражнения, прошедшие проверку. Устаревший, сломанный или отсутствующий профиль немедленно ведёт к табличному ответу.
- [ ] Следить за долей fallback, временем ответа, возрастом профиля, ошибками сетки и расхождением прогнозов. Версию модели можно отключить без миграции клиентских данных.

Общую популяционную модель рассматривать как следующий технический этап после появления многопользовательского датасета и доказанной пользы поверх личной калибровки. Она не входит в зависимость этапов 1–5.

## Критерии приёмки

| Контур | Проверяемое условие |
| --- | --- |
| Холодный старт | При нуле наблюдений сервис и Flutter, включая офлайн-режим, дают результаты канонической таблицы с одинаковым hash/диапазоном; персональные таблицы БД могут быть пустыми. |
| Сквозное редактирование | Изменённые Flutter вес, повторы, RPE и порядок проходят Gateway → `workouts-service` → обратное чтение без потери полей. |
| Чистота фактов | Подход без ответа никогда не получает `user_reported`; независимый ввод и подтверждение подсказки различимы, импорт не выдаётся за ответ пользователя; сохраняются фактические вес, повторы, сессия, время и версия прогноза. |
| Коррекции | Все пути completion используют одну транзакционную запись; повтор операции возвращает тот же ответ, устаревшая ревизия получает конфликт, отмена исключает один факт на `(session_id, set_id)` из подбора. |
| CDC | На контрольных событиях PostgreSQL и ClickHouse согласованы по идентификатору, `revision`, источнику RPE и статусу; равные timestamps, replay, `NUMERIC` и tombstones обработаны детерминированно. |
| Математика | Недостижимые ячейки не превращаются в один повтор; сетка монотонна; прямые и обратные расчёты согласованы в документированных пределах округления. |
| Совместимость | Старые HTTP/gRPC и Flutter-клиенты продолжают вычислять и завершать подходы; новый формат дробного RPE не подменяет старый молча. |
| Изоляция | Пользователь не может записать наблюдение в чужую сессию или получить чужую сетку, включая подмену `X-User-Id`. |
| Персонализация | Версионированное правило проверяет информативность, as-of силу, границу ошибки в области применения и отсутствие ухудшения на будущих сессиях; при недостатке данных остаётся теневая версия и таблица. |
| Откат | Возврат к предыдущей полной версии (`k`, `g`, область, сетка) и отключение персонального расчёта проверены при конкурентных чтениях и, если введён, работающем кэше в пределах заданной задержки. |

До появления реальных подтверждённых RPE нельзя подтвердить целевой `RPE MAE ≤ 0.4` или статистически значимое улучшение. Это измерения для этапа 4, а не критерии выпуска калькулятора с таблицей.
