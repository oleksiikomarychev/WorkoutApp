# WorkoutApp: правила разработки

## Перед изменением

- Прочитай [процесс](docs/development/README.md), относящиеся к задаче specs в
  `openspec/specs/`, активный change, решения `docs/decisions/` и случаи `docs/edge-cases/`.
  Ищи по сервису, capability и ключевым словам; не загружай весь архив.
- Проверяй вложенные `AGENTS.md` в изменяемых каталогах. Локальные правила добавляем,
  когда у сервиса появляются собственные устойчивые ограничения.
- Для нового change используй [карту возможностей](docs/architecture/system-map.md)
  и [анализ влияния](docs/architecture/change-impact.md): определи затронутые границы,
  потребителей и применимые семейства контрактов. Учитывай статус каждого раздела
  каталога: [ACCESS принят](docs/decisions/DEC-20261112-access-contract.md),
  [EXEC принят](docs/decisions/DEC-20261112-operation-execution-contract.md),
  [DATA принят](docs/decisions/DEC-20261112-data-semantics-contract.md),
  [EVENT принят](docs/decisions/DEC-20261112-event-delivery-contract.md),
  [READY принят](docs/decisions/DEC-20261112-capability-readiness-contract.md),
  [COMPAT принят](docs/decisions/DEC-20261112-contract-compatibility.md). Расширяй main
  specs только проверенным согласованным поведением.
- Различай наблюдаемое поведение, согласованное требование и своё предложение.
  Код и существующий тест сами по себе не означают согласования продуктового поведения.
- Новые области спецификаций предлагай владельцу небольшими порциями: зачем, границы,
  сценарии, открытые вопросы. Выбор области разрешает подготовить проект спецификации,
  но не означает принятия всех требований. Уже согласованный объём не требует повторного разрешения.

## Работа с изменениями

- Для нового поведения, изменения контракта или межсервисного взаимодействия используй
  OpenSpec `spec-driven`: proposal, specs, design по необходимости, tasks.
  Для локального исправления согласованного поведения и документации отдельный change
  не обязателен. Если ожидаемое поведение неясно, сначала уточни его.
- Не расширяй задачу рефакторингом соседних сервисов. HTTP, WebSocket, protobuf,
  события и миграции проверяй со стороны затронутых потребителей. Если контракт требует
  правки доступного клиента, обнови и проверь вызывающий сценарий до завершения change.
- Редактируй исходные `.proto`, затем генерируй stubs существующим инструментом;
  не исправляй сгенерированные файлы вручную.
- Edge case сохраняй по [шаблону](docs/edge-cases/TEMPLATE.md). Повторяющийся случай
  дополняй, а не дублируй. По возможности воспроизведи до исправления и сохрани
  регрессионный тест рядом с кодом соответствующего сервиса.
- Договорённости сохраняй по [шаблону решения](docs/decisions/TEMPLATE.md).
  `accepted` требует реального основания согласования; своё предложение оставляй
  `proposed`. Не выдумывай историю обсуждений или согласие пользователя.
- Обсуждение и новые пояснения пиши на русском; идентификаторы, команды и обязательные
  заголовки OpenSpec сохраняй в требуемом инструментом формате.

## Проверка и завершение

- Соблюдай [критерий завершения change](docs/development/change-completion.md): для
  каждого изменённого требования в существующем tasks/verification укажи сценарий,
  проверку, результат и ограничения. Непроверенная обязательная гарантия блокирует
  завершение; отметки tasks и структурная валидация не заменяют доказательств.
- Перед commit/push выполняй настроенные hooks. Для предварительного выбора
  проверок используй `python3 scripts/check_changed.py --worktree --list`.
- Выбирай проверки по затронутому поведению: тест сервиса, интеграционный тест границы,
  E2E при изменении пользовательского потока. Сначала изучи fixtures и зависимости;
  единой подтверждённой команды тестирования всех сервисов пока нет.
- Для бага проверяй причинную связь: тест падает из-за исходного дефекта и проходит
  после исправления. Если воспроизведение недоступно, явно сохрани ограничение.
- Для изменённых OpenSpec-артефактов выполни
  `openspec validate --all --strict --no-interactive`. Валидатор проверяет структуру,
  а не принятие требований или корректность реализации.
- Обнови затронутые требования, edge cases и решения. Перед архивированием change
  сверь реализацию и проверки, синхронизируй delta specs с основными specs.
- В результате укажи изменение, выполненные проверки и непроверенные места.
  Не называй пропущенные, заблокированные или только собранные тесты прошедшими.
- Для воспроизведения используй минимальные синтетические данные; не помещай секреты,
  production payloads или персональные данные в артефакты.
